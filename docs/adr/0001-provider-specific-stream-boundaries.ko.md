# ADR 0001: 거래소 전용 스트림 계약을 공통 스트림과 분리한다

[English](0001-provider-specific-stream-boundaries.md) | [한국어](0001-provider-specific-stream-boundaries.ko.md)

- 상태(Status): 승인됨(Accepted)
- 결정일(Date): 2026-08-14

## 배경

`Client::subscribe`와 `Client::subscribe_account`는 공통 실시간 스트림 계약을
제공합니다. 두 호출은 각각 `MarketStream`, `AccountStream`을 반환하고, 이벤트는
의도적으로 정규화된 `MarketEvent`, `AccountEvent`로 전달됩니다.

일부 거래소 스트림에는 안정적인 공통 의미가 없는 추가 정보가 있습니다. 예를 들어
Hyperliquid는 체결 hash와 참여 계정, 호가 단계별 주문 수, 캔들의 체결 수, 거래소 주문
상태 상세, Spot 진입 명목가치를 보냅니다. 현재 공통 스트림은 이 필드를 의도적으로
노출하지 않습니다. [Hyperliquid 스트림 계약](../providers/hyperliquid.ko.md#스트림)과
[공식 WebSocket 구독 스키마](https://hyperliquid.gitbook.io/hyperliquid-docs/for-developers/api/websocket/subscriptions)를 참고하세요.

같은 공통 이벤트 타입은 Rust, Python, Dart, TypeScript에서 모두 공개됩니다. 공통
타입에 거래소 전용 선택 필드나 전역 확장 객체를 추가하면 모든 거래소와 바인딩이 한
거래소의 데이터 모델에 결합됩니다.

## 결정

1. `Client`, `MarketStream`, `AccountStream`, `MarketEvent`, `AccountEvent`는
   안정적인 정규화 공통 계약으로 유지합니다.
2. 원본 의미를 보존해야 하는 실시간 데이터는 거래소 전용 어댑터 API와 거래소 전용
   tagged event 타입으로 노출합니다. 거래소 전용 이벤트는 정규화 공통 값과 문서화된
   원본 필드를 함께 가질 수 있습니다.
3. 문서화된 거래소 필드는 타입이 있는 필드로 노출합니다. 필요하면 미래 호환 보존을
   위해 `raw_json`을 둘 수 있지만, 이것은 타입이 있는 필드를 대체하지 않습니다.
4. 필드를 공통 모델로 승격하려면 거래소와 무관한 의미, 단위, 결측 규칙, 검증 계약을
   명시적으로 확정합니다. 보통 둘 이상의 거래소 근거가 필요합니다.
5. 두 번째 구체적 거래소 전용 스트림이 같은 구조를 실제로 요구하기 전에는 범용 공개
   `ProviderStream<T>` 추상화를 만들지 않습니다. 기존 연결 종료, 재연결,
   backpressure 동작을 재사용합니다.

예를 들어 이후 Hyperliquid 전용 체결 이벤트에는 정규화된 `Trade`와 Hyperliquid만의
hash, 참여자, 원본 체결 식별자를 함께 둡니다. 이 필드를 모든 거래소의 `Trade`에
추가하지 않습니다.

## 결과

- 공통 스트림 사용자는 거래소가 달라도 작고 이식성 있는 API를 유지합니다.
- 고급 사용자는 공통 이벤트를 downcast하거나 타입 없는 JSON을 해석하지 않고도
  거래소 전용 데이터를 받을 수 있습니다.
- 새 거래소의 원본 스트림을 추가해도 해당 거래소의 타입, 스키마, 바인딩, fixture,
  문서만 바뀌며 모든 공통 이벤트 사용자가 영향을 받지 않습니다.
- 거래소 전용 스트림도 공개 API이므로 완료로 표시하기 전에 스키마와 지원 언어 전체
  바인딩을 통해 구현해야 합니다.
- Hyperliquid 공통 스트림의 결손 6개는 이 결정의 범위입니다. 구현은 서로 무관한 공통
  이벤트 6개 변경이 아니라 하나의 거래소 전용 스트림 배치로 처리합니다.

## 범위 밖

Upbit `LIST_SUBSCRIPTIONS`는 거래소 데이터 확장이 아니라 연결 제어 작업입니다. 현재
구현은 기존 `MarketStream`을 조회하지 않고 임시 socket을 엽니다. 이 동작을 바꾸려면
양방향 스트림 제어에 관한 별도 결정을 내려야 합니다.

platform-limited 작업은 별도 서비스 또는 명시적인 차단 결정으로 남습니다. 이 ADR은
그 작업의 어댑터 경계를 바꾸지 않습니다.

## 기각한 대안

### 공통 모델에 거래소 전용 필드를 `Option`으로 추가

모든 거래소와 바인딩이 거래소 전용 개념을 함께 가지게 됩니다. 필드 소유 거래소가
불명확해지고, 보통의 모델 변경도 전역 호환성 변경이 됩니다.

### 공통 이벤트에 하나의 범용 거래소 확장 객체를 추가

결합을 큰 교차거래소 union으로 옮길 뿐입니다. 여전히 모든 바인딩이 모든 거래소의
원본 데이터를 알아야 합니다.

### 거래소 전용 필드를 버림

원본 의미가 필요한 클라이언트를 지원할 수 없고, 문서화한 거래소 전용 API 정책에도
맞지 않습니다.
